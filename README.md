# 诚本 APS 生产计划排程助手

面向制造业计划人员的对话式查询助手，将“查计划、核对物料、查看派工”组织为自然语言提问、简短结论和可追溯明细。

本项目展示我如何把业务问题映射为受约束的工具调用，设计模型与业务数据的分工，并通过关联场景和异常案例完善交互。当前阶段提供只读查询，公开版本包含 13 个模拟订单，支持无密钥演示模式和配置模型后的工具调用模式。

![自然语言查询与生产计划总览](docs/screenshots/chat.png)

## 业务问题与产品目标

计划人员围绕同一订单，可能连续核对“怎么安排、物料是否齐套、是否形成派工”。这些问题对应不同的业务记录与判断口径，用户需要选择查询入口、设置条件，再将结果放在一起理解。“已排完整”“生产完成”“已下发现场”也分别代表不同含义，回答中的一次混淆就可能影响后续判断。

产品目标是让用户用业务语言提出问题，先获得简短结论，再进入支持该结论的记录核对。第一阶段复用已有排程信息，聚焦查询、理解和证据展示；执行改排涉及业务规则与授权，需要另行验证。

## 我的工作与交付

- **场景与需求**：梳理原系统流程和数据口径，将计划总览、交期风险、单订单排程、齐套与派工问题整理为查询场景和验收要求。
- **AI 交互设计**：定义问题到工具的映射、参数范围、模型回答边界，以及“结论 → 摘要卡 → 详情”的展示方式。
- **原型与验证**：借助 AI 辅助编码推进原型，将 13 个模拟订单的三类记录关联，并围绕来源说明、图表筛选、连接与重试设计回归检查。

主要交付为场景说明、工具整理方案、模型与展示协议、可运行原型及验证材料。公开材料见[产品设计说明](docs/product-design.md)和[验证记录](docs/verification.md)。

## 关键产品决策与 AI 分工

| 产品决策 | 判断依据 | 落地方式 |
|---|---|---|
| 按业务查询能力组织工具 | 多个提问入口可能使用同一种数据能力，筛选条件决定具体结果 | 6 个首页入口由 5 个业务工具承接，“计划总览”和“未完整排入”共用工具 |
| 业务事实由工具生成 | 数量、状态和日期需要一致且可复核 | 模型识别意图与条件，工具生成事实，前端按固定类型展示 |
| 摘要与完整明细分开传递 | 用户需要先理解结论，再按需核对；完整图表数据无需进入模型上下文 | 模型只接收简短事实，完整 UI 数据直接交给前端渲染 |
| 将来源与不确定性明确展示 | 模型参与回答时，用户仍需知道数据是否实时、是否完整 | 每次结果标明来源、取数时间和范围，未取得证据时说明限制 |

核心链路为：**用户问题 → 模型识别意图与查询条件 → 业务工具生成事实 → 简短回答与固定图表 → 用户查看明细**。

AI 承担从业务语言到查询能力的转换和结果概述；计划计算、状态判定与图表数据保持确定性。默认 `demo` 模式使用规则路由，便于直接体验；`model` 模式通过 Semantic Kernel 调用模型选择工具，两种模式都可以使用同一份模拟快照。

## 一个跨场景的用户任务

以演示订单 `Z9900001` 为例，连续询问：

1. **“演示订单 Z9900001 怎么安排？”** 查看日期、工段、班次与产线，展开矩阵式甘特表核对计划记录。
2. **“演示订单 Z9900001 的物料齐套状态如何？”** 查看快照标记、订单—物料矩阵及库存或供应证据，保留未取得的结论。
3. **“演示订单 Z9900001 派工了吗？”** 查看关联任务，点击产线状态柱形筛选明细，分别核对订单号、任务号和产线。

三类查询使用一致的订单、数量和模拟取数时点。这样的关联支持用户连续核对同一对象，各类记录仍按各自口径解释：排入计划不能直接证明生产完成，任务在制不能直接证明已下发现场。

## 代表性迭代与验证

| 发现的问题 | 产品调整 | 验证重点 |
|---|---|---|
| 计划、物料、派工样本分散，连续查询同一订单时难以核对 | 统一 13 个模拟订单及相关记录，同步模型提示词中的能力说明 | 同订单跨三场景的数量、产品和取数时间一致，独立入口仍可使用 |
| 点击某产线的任务状态柱形后，明细未同时限定产线 | 明细同时按产线和状态筛选，展示筛选条件，并分列订单与任务标识 | 两条产线存在同状态任务时，只展示点击产线的对应任务 |
| 重新生成失败或停止时，旧结果与输入可能丢失 | 保留旧回答、卡片和草稿，新回答成功后标识先前回答 | 失败、停止及刷新后可恢复；后续模型历史使用最新成功回答 |

评测按“问题类型 → 工具选择 → 查询范围 → 回答与明细一致性 → 失败恢复”组织。固定问题评测与工程测试分别记录，避免把单元测试通过率当作模型回答准确率。

作品集发布检查通过前端构建、29 项前端测试、35 项后端单元测试、关联订单接口核对和 6 项浏览器回归；实际演示服务中的三次连续查询与详情展开也已检查。上述发布检查使用 `demo` 模式；模型工具调用评测需要配置模型后单独运行。详情见[验证记录](docs/verification.md)。

**阶段成果**：已形成业务问题、工具协议、交互展示和验证用例相互对应的只读原型。当前未实现插单、自动改排、派工下发或业务写回，尚无生产上线后的效率与采纳数据。真实订单快照适配代码保留，公开仓库仅携带模拟数据。

## 体验原型

需要 Docker 与 Docker Compose。在仓库根目录首次执行：

```bash
cp .env.example .env
docker compose --env-file .env up -d --build --wait
```

Windows PowerShell 首条命令为 `Copy-Item .env.example .env`；已有配置时保留原文件。打开 <http://127.0.0.1:19440/>，按照上面的三个问题体验同一订单的连续查询。

默认 `AGENT_MODE=demo` 无需密钥。体验模型工具调用时，在本地 `.env` 中设置 `AGENT_MODE=model`，填写 `SK_ENDPOINT`、`SK_API_KEY`、`SK_MODEL_ID`，再执行 Compose 启动命令。模型模式的数据仍为模拟快照。语音是可选能力，需要另行配置供应商服务。

前端采用 Vue 3 / Vite / Pinia / ECharts，后端采用 ASP.NET Core 6 / Semantic Kernel，通过 SSE 返回回答与展示数据。

```bash
pnpm --dir web-frontend install --frozen-lockfile
pnpm --dir web-frontend build
node --test tests/frontend/*.test.mjs
dotnet test tests/unit/WePilot.Tests.csproj -c Release
node tests/interfaces/linked-demo.mjs
node tests/interfaces/order-dispatch.mjs
```

后端单元测试需要 .NET 6 SDK，接口测试需要启动服务。`tests/agent-evals/linked-demo.mjs` 用于模型模式的关联订单工具调用评测。

模拟快照取数时间为 `2026-09-26 17:30`，不代表实时生产状态。停止本项目容器：`docker compose --env-file .env down`。
